# AGENTS.md

Rules AI coding agents (Claude, Cursor, Kilo, Codex, Gemini, Copilot) MUST follow when contributing to the Crab Super App monorepo. Human contributors should follow [CONTRIBUTING.md](CONTRIBUTING.md); agents must follow that document AND every rule below.

If any rule here conflicts with a default behaviour of your tooling, this file wins.

## 1. Repo Structure

```
Crab_Mobile_Flutter/
├── apps/
│   ├── backend/          NestJS microservices (gateway, auth, user, ride, food,
│   │                     payment, chat, notification, rating)
│   ├── mobile/           Flutter 3.x app (BLoC, GetIt, GoRouter, Dio)
│   └── web-admin/        React 18 + Vite + TypeScript + TailwindCSS + shadcn/ui
├── packages/
│   ├── common-types/     Shared TypeScript enums, DTOs, interfaces
│   └── socket-events/    Shared Socket.IO event types
├── docker/               docker-compose.dev.yml + service Dockerfiles
├── docs/                 Public technical documentation (see docs/INDEX.md)
└── .github/workflows/    CI / docker publish / scanners
```

Do not introduce new top-level directories without an ADR under `docs/adr/`.

## 3. Build & Verify (run before claiming completion)

From repo root, in this order:

```bash
pnpm install --frozen-lockfile
pnpm lint
pnpm typecheck      # if not wired into lint, run tsc --noEmit per workspace
pnpm test
pnpm build
```

For `apps/mobile`:

```bash
cd apps/mobile
flutter pub get
flutter analyze
flutter test
```

If you only touched a single workspace, you may scope with `pnpm --filter <pkg> <script>` but the final verification before opening a PR must be the full set above. Never claim "done" without running the relevant commands and reporting their output. See the verification policy in CONTRIBUTING.md.

## 4. Commit Hygiene

- Use [Conventional Commits](https://www.conventionalcommits.org/): `<type>(<scope>): <subject>`.
  Allowed types: `feat`, `fix`, `docs`, `style`, `refactor`, `perf`, `test`, `build`, `ci`, `chore`, `revert`, `infra`.
- Subject line ≤ 72 characters, imperative mood, no trailing period.
- One commit per logical concern. Each commit must build cleanly on its own.
- Stage explicit paths (`git add path/to/file`). Never run `git add .` or `git add -A` without first inspecting `git status`.
- Body explains the **why**, not the diff.

### Forbidden in commit messages (zero tolerance)

- `Co-Authored-By: Claude <noreply@anthropic.com>` or any AI / bot co-author trailer.
- `🤖 Generated with Claude Code`, `Generated by AI`, or similar markers.
- Any reference to the agent that produced the change.

## 5. Files Agents MUST NOT Commit

These are private artefacts and never belong in the public repo. Most are already in `.gitignore`; agents must respect the spirit, not just the letter.

- Personal planning notes: `PLAN*.md`, `NOTES*.md`, `TODO*.md`, `ROADMAP*.md`, `DRAFT*.md`, `*.private.md`, `*.local.md`.
- Internal templates / rule files: `DOCUMENTATION_MASTER.md`, `RULES.md`.
- Tooling state directories: `.claude/`, `.omc/`, `.kilo/`, `.playwright-mcp/`, `.claude-private/`.
- Secrets and env files: `.env`, `.env.local`, `.env.*.local`, anything containing tokens, API keys, JWT secrets, database URLs with credentials, or private keys (`*.pem`, `*.key`).
- Build outputs: `dist/`, `build/`, `.next/`, `coverage/`, `.turbo/`, Flutter `.dart_tool/`, `*.apk`, `*.aab`, `*.ipa`.

If you discover a private file already committed, stop and surface it to a human; do not silently rewrite history.

## 6. Chunked Writes

Tooling has ~2–3 minute per-call timeouts. To stay safe:

- **Never write or edit more than 300 lines in a single tool call.**
- For a new file longer than 300 lines, write an initial chunk then append in further operations.
- For edits to existing files, prefer surgical replacements over full-file rewrites.
- Split large code generation into logical sections (imports, types, functions) and write each as its own operation.

Smaller, focused operations are faster and more reliable than one giant write.

## 7. Branches and Pull Requests

- Never push directly to `main`. Always work on a topic branch:
  - `feature/<short-desc>`, `fix/<issue-num>-<desc>`, `chore/<short-desc>`, `infra/<short-desc>`.
- Open the PR against `main` with a Conventional Commits style title (≤ 70 chars).
- PR body must cover: why, what changed at a high level, how it was tested, linked issues, and screenshots for any UI change.
- All CI checks must be green before requesting review. Do not merge a red PR.
- Do not force-push during review unless explicitly asked.
- For UI changes, screenshots must show populated, signed-in success states — never empty lists, 404s, or loading skeletons.

## 8. Status Vocabulary (canonical)

These string literals are the source of truth across mobile, web-admin, and backend services. Do not invent synonyms (`finished`, `done`, `cancel`).

```
RideStatus  = REQUESTED | MATCHED | PICKUP | IN_PROGRESS | COMPLETED | CANCELLED
OrderStatus = PLACED | CONFIRMED | PREPARING | READY | PICKED_UP | DELIVERED | CANCELLED
```

State transitions live in `docs/RIDE_MATCHING.md` and `docs/FOOD_DELIVERY.md`. Any new status must ship with an ADR and updates to both shared types and consumer clients.

## 9. API Conventions

- REST base path is `/api/v1`. Never hard-code `/api` or `/v1` in isolation.
- Public endpoints are catalogued in `docs/API.md`; Socket.IO events in `docs/WEBSOCKET_EVENTS.md`.
- Every mutating route (`POST` / `PATCH` / `PUT` / `DELETE`) must validate input with `class-validator` (NestJS) or zod before touching the database.
- Update `packages/common-types` and `packages/socket-events` whenever an enum, DTO, or event payload changes, then run the full verify suite (section 3).

## 10. Asking Questions

- Open a GitHub issue: <https://github.com/JasonTM17/Crab_Mobile_Flutter/issues>.
- Bugs: include reproduction steps, expected vs actual behaviour, environment, and logs.
- Security issues: do not file a public issue — follow [SECURITY.md](SECURITY.md).
- Feature ideas: describe the user problem first, code second.
